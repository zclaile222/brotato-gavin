# Git 历史丢失与恢复记录

> 本文件记录 2026-09-15 / 2026-09-17 两次 `.git` 对象库损毁事故的取证结论。
> 保留此文件是为了让「为什么历史从这里开始」这件事有据可查，而不是变成一段口口相传的传说。

## 结论速览

- **两次事故的成因不同，第一次的归因不能套用到第二次。**
- 提交历史链**在 reflog 中完整保留**，但**对象库（blob/tree/commit 实体）已不可恢复**。
- 因此本仓库以 **2026-09-17 的工作区现状为新基线**，历史自此重新开始。
- 新基线之前有 **186 个提交**（至 `558b585`），其后有 5 个（至 `984d68f`），**内容已丢失，仅存 ref 名称**。

## 事故一：2026-09-15

| 项 | 记录 |
|---|---|
| 现象 | `.git/objects/**` 被清空 —— 63 个分片目录存在但 **0 个对象**；无 pack；`refs/`、`worktrees/` 整个消失 |
| 删除路径 | **直接 unlink**（git 是 C 程序，不经过 Node 层拦截） |
| 回收站证据 | `objects/` 相关记录 **0 条** —— 回收站里找不到 |
| 当时状态 | 4 个 `git worktree` 并发提交 |
| 形态特征 | 「`gc`/`repack` 中途被打断」：松散对象已删、pack 从未写成、松散 ref 也没了 |

**归因：** git 自身的后台维护（`gc`/`repack`）与并发操作竞争，维护流程被打断在「已删松散对象、尚未写出 pack」的中间态上。

**该归因仅对本次成立。** 见事故二。

### 删除机制（已定位到代码）

WorkBuddy 的安全删除层通过 `BASH_ENV` 注入每个子进程：

| 层 | 文件 | 行为 |
|---|---|---|
| bash | `cli/vendor/shim/safe-bin/safe-delete-bash-env.sh` | 覆写 `rm` / `unlink` / `rmdir` |
| Node | `cli/vendor/shim/node-safe-delete-shim.cjs:807` | patch `fs.unlinkSync` / `fs.rmdirSync` / `fs.rmSync` |
| 执行 | `cli/vendor/shim/safe-delete-broker-delete.cjs:33` | `deleteMode: 'trash'` —— **一律走回收站** |
| 守卫 | `cli/vendor/shim/safe-delete-bulk-guard.cjs` | ≥20 项需人工确认（保护机制，非破坏） |

绕过白名单（`shouldBypassSafeDelete`，同文件 `:172-178`）仅 5 类：
OS 临时目录 / npm cache 临时目录 / npm cache 日志 / WorkBuddy 托管的 Node 安装暂存 / pnpm virtual store。

**`.git` 不在白名单内** → 若经此层删除，必然进回收站 → 与观察到的事实吻合。

> 附注：这也解释了为何本机 bash 中 `ls` / `head` / `grep` 等命令不可用 —— 是这套 shim 的设计使然，不是环境损坏。

### 未能闭合的一环

「**哪个** Node 进程发起了对 `.git` 的删除」**没有证据**。

- 删除者日志由环境变量 `CODEBUDDY_SAFE_DELETE_REPORT_PATH` 开启（见 `node-safe-delete-shim.cjs:180-196` 的 `recordTrash`）
- 事故当时该变量**未设置** → 无删除者记录

**此环节保持「未知」，不做推测性归因。** 若未来再次发生，**务必先设置该环境变量**，它会把每次 trash 操作的路径与时间戳落盘。

## 教训

1. **本机对象库不能是唯一副本。** 两次事故都证明了这一点 —— 有远端就是有安全网。
2. **不要把「已知偶发」当作免责理由。** 第一次事故的归因在第二次条件下不成立，若当时就把结论钉死为「并发 git 操作」，第二次会完全无从下手。
3. **取证要留证据链。** 这次能还原到 reflog 链条，全靠 `.git` 走了回收站（而非直接 unlink）—— 而这一点本身也是证据。
4. **建议保持 `CODEBUDDY_SAFE_DELETE_REPORT_PATH` 有值**，代价极小，下次事故能直接定位到调用者。
